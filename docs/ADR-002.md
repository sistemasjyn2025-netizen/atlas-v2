# ADR-002: Geometry Representation Strategy

**Date:** 2026-07-11  
**Status:** Accepted  

## Context
ATLAS requires a robust geometric foundation to handle parametric structural engineering models. It is critical that this foundation is independent of any rendering framework (like Three.js or WebGL) or CAD exporting tools. The geometry must be mathematically precise and serve as the single source of truth for all engineering calculations (clash detection, volume, mass, bounding boxes).

## Decision
We will divide the geometry ecosystem into two core packages:
1. `@atlas/geometry-core`: Defines pure mathematical and structural primitives (`Point3D`, `Vector3D`, `Line`, `Plane`, `Curve`, `Section`, `Profile`, `Extrusion`, `Solid`). It contains no computational logic, only type definitions.
2. `@atlas/geometry-engine`: Contains the operational logic to generate, manipulate, and query geometry.

### Engineering-First Approach
Instead of generating generic meshes immediately, we represent structural elements as mathematical extrusions and boundary representations (B-Rep). 
For example, a steel column is not stored as thousands of triangles. It is stored as:
- A `Profile` (e.g., IPN120).
- A `Path` (e.g., a `Line` from point A to point B).
- A `Transform` (spatial orientation).

When a rendering system or CAD exporter needs a mesh or a DWG file, it will interpret this pure `Solid` definition and triangulate/tessellate it on the fly.

## Consequences
- **Pros:** 
  - Ultra-lightweight `.atlas` files.
  - Mathematically perfect calculations (volume, intersections).
  - Absolute decoupling from UI or rendering engines.
- **Cons:**
  - Rendering layers will have to build their own tessellators or rely on an intermediary meshing service.
